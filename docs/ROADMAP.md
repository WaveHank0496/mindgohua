# 上架路線圖

> 這份文件的用途：讓**不讀程式碼的人**也能判斷專案現在在哪、下一步是什麼、
> 以及「我說做完了」是不是真的做完了。
>
> 目標：把 `Mindgohua_Spec.md` 的 prototype 變成一個能在 **Google Play 公開上架**、
> 陌生人裝了也不會壞掉的 app。
>
> 最後更新：2026-09-17

## 已經定案的四個決定

這四件事決定了後面所有工作的形狀，改動任何一個都要回頭改這份路線圖。

| 決定 | 選擇 | 影響 |
|---|---|---|
| 終點 | **上架 Google Play** | 需要隱私政策、release 簽章、商店素材、封測流程 |
| Crash 回報 | **堅持零網路**，做本機記錄 + 使用者手動匯出 | 保住「無 INTERNET 權限」這個核心差異化；代價是看不到沒主動回報的當機 |
| 測試裝置 | OPPO Reno7（ColorOS）一台為主 | OEM 相容做成「對照表 + 失效自我偵測」，不逐台驗證 |
| 協作節奏 | 全權推進，只在需要實機測試時停 | 每個里程碑結束會給一份你看得懂的驗收清單 |

## 你的角色

你不需要看懂程式碼。你需要做的只有三件事，而這三件事我都做不到：

1. **實機驗收。** 每個里程碑結束我會給一份白話清單，你照著在手機上點一遍。
   清單上任何一條做不到，就是沒完成，不管程式碼看起來多漂亮。
2. **產品取捨。** 文案、預設值、貓長什麼樣、要不要加某個功能。這些沒有標準答案，只有你的答案。
3. **踩煞車。** 當我說出「這個先跳過」「之後再補」「應該沒問題」——
   這三句話出現時，要求我說清楚代價是什麼。

### ✅ M0 — 建立基準線

在還沒確認「現有的東西真的能跑」之前就開始改，是最常見的災難起點：
之後出問題會分不清是本來就壞的，還是新改壞的。

- [x] 盤點現有程式碼與文件
- [x] 跑完整單元測試，確認全綠
- [x] 建立 CI（`.github/workflows/ci.yml`）——每次 push 自動跑測試 + 建置 APK
- [x] 推上 GitHub，確認 CI 在雲端也是綠的

**基準線（2026-09-16 實測）：42 個測試全數通過，0 失敗、0 略過。**

| 測試類別 | 測試數 |
|---|---|
| `SessionEngineTest` | 14 |
| `ItemAdvanceCounterTest` | 11 |
| `ScrollRhythmAnalyzerTest` | 8 |
| `DayBoundaryTest` | 6 |
| `PrivacyInvariantTest` | 3 |

**實際遇到什麼：** 第一次跑出現 `BUILD SUCCESSFUL`，但仔細看輸出是
`testDebugUnitTest UP-TO-DATE` / `22 actionable tasks: 22 up-to-date`——
Gradle 判斷程式碼沒變，直接沿用上次的結果，**一個測試都沒有真的執行**。
要強迫它跑要加 `--rerun`。

這是個值得記住的教訓：綠色的「成功」不等於「驗證過」。
之後只要是要當作判斷依據的測試結果，都要確認它真的執行了，而且跑了幾個。

**CI 首次雲端執行：** 第一次失敗，第二次全綠（run 35005737944，10 個步驟全過）。
產物：`test-reports` 38 KB、`mindgohua-debug-apk` 8.72 MB。

第一次失敗的是 `android-actions/setup-android@v3` 這一步，而它是「為了保險」才加的 ——
GitHub 的 ubuntu runner 本來就預裝 Android SDK 且授權已接受，這個專案並不需要它。
移除之後其餘步驟全數通過，證實它確實多餘。

> **教訓：為了防範假想問題而加的依賴，成了整條管線唯一的真實故障點。**
> 每多一個外部依賴就多一個會壞的東西，而且壞的時候未必看得出是誰壞的。

另外一個過程中的誤判值得記下來：一度判定 `gradlew` 是 CRLF 結尾、會讓 Linux CI 失敗，
還據此推論「CI 一定是紅的」。實際上 `gradlew` 從頭到尾都是正確的 LF ——
錯的是檢查方法：`grep -c $'\r'` 在 Git Bash 裡 `\r` 會被吃掉變成空 pattern，
而**空 pattern 會匹配每一行**，所以「252 行含 CR」其實只是檔案的總行數。

> **教訓：在相信量測結果之前，先確認量測工具本身是對的。**
> 一個壞掉的檢查會給出看起來很具體、很有說服力的假證據。

**你要做的事：** 無。這關結束後你會在 GitHub 專案頁上看到一個綠色勾勾。

### 🟨 M1 — 補上缺的地基

現在這個專案只能做出 debug 版（開發用、不能上架）。這關把它變成「可以發布」的狀態。

- [x] Release 簽章設定（keystore 從本機檔案讀，**絕不進 git**）
- [x] **本機 crash 記錄**：app 爆掉時寫進手機本機檔案
- [x] 設定頁加「匯出診斷記錄」按鈕，使用者自己決定要不要傳給你
- [x] **當機寫入路徑的驗收方法**（已解決，見下）
- [x] `targetSdk` 34 → 35（Play 對新上架 app 的要求）——已於 OPPO Reno7 實機驗收，
      overlay、倒數、長按解除、診斷卡片皆正常
- [ ] 版本號規則：`versionCode` 自動遞增、`versionName` 語意化
- [ ] 開啟 R8 程式碼壓縮並確認不會壓壞 Compose / DataStore

**R8 的實際效益（已量測）：** release APK 18.73 MB，其中 **18.16 MB 是 dex**，
原生函式庫四個 ABI 合計只有 0.06 MB。也就是說體積幾乎全是 bytecode，
正是 R8 要處理的東西。目前 `isMinifyEnabled = false`。

**測試數：55（原 42 → 加入當機紀錄後 55）。**

#### 那個「無解」的缺口其實是假問題

原本記錄的缺口是：要驗證「當機時真的會寫出檔案」，就得**故意讓 app 崩潰**，
而正式版裡不該留一顆「讓 app 當機」的按鈕，所以看起來無解。

實際上崩潰只是**觸發條件**，真正要驗的是檔案有沒有被正確寫出來、輪替有沒有生效、
讀不讀得回來 —— 而這些**完全不需要 Android**。把檔案操作抽成只吃 `File` 的函式，
一般單元測試就驗得了，不需要手機也不需要模擬器。

> **教訓：當一個東西「看起來沒辦法測」，先確認你要測的到底是什麼。**
> 常常是把觸發條件和待驗行為綁在一起看，才顯得無解。

#### 仍然沒有覆蓋的部分（需實機，屬手動驗收）

1. 系統是否真的會呼叫 `setDefaultUncaughtExceptionHandler`
2. 按下「匯出診斷紀錄」後，檔案是否真的寫進使用者選定的位置（SAF）

這兩項本質上需要真實的 Android 系統參與，不是抽換寫法就能繞過的。
它們會進手動驗收清單，不會假裝已經驗過。

**你要做的事：** 產生一個 keystore（一個檔案 + 兩組密碼，等於這個 app 的身分證）。
我會給你指令，但密碼必須你自己設、自己保管——**這個檔案弄丟，這個 app 就永遠無法再更新**。

### 🟨 M2 — 自由選 app + 去 OPPO 化

- [x] **使用者可自由挑選要看住的 app**（原本只有寫死的 7 個）
- [x] `Build.MANUFACTURER` → 各廠牌自啟動設定頁的對照表（OPPO / 小米 / vivo / 華為 / Samsung / OnePlus / ASUS / 近原生）
- [x] 設定頁文案隨廠牌變，而不是一律講 ColorOS
- [x] 找不到對照表項目時的退路（退回系統設定頁 + 文字步驟）
- [ ] 「貓好像沒在運作」的主動提醒：`SurvivalLog` 已經能偵測服務被殺，
      但目前只有你打開 app 才看得到。要讓它主動告訴使用者。

**測試數：79（M1 結束時 55 → 加入 app 挑選 12 + 廠牌對照 12 後 79）。**

#### 自由選 app：底層一行都沒改

原本以為要大改，實際上偵測端三處（`UsageStatsDetector`、`ScrollAccessibilityDetector`、
`ScrollWatchService`）吃的一直是**一個字串集合**，從不在乎那些字串來自哪裡。
真正的限制只在兩個地方：UI 寫死的 `selectable` 清單，以及 Manifest 的 `<queries>` 白名單。

> **教訓：「加功能很難」常常是假設，不是事實。先查清楚現有程式碼真正的限制在哪。**

刻意**不用** `QUERY_ALL_PACKAGES`：那是 Google Play 列管的敏感權限，
上架要填表說明用途且核准與否不在我們手上。改成查詢有 LAUNCHER 入口的 app，
不需任何敏感權限，而查不到的只有沒有桌面圖示的系統元件 —— 本來就沒人拿來滑。

#### 一個我自己犯的測試設計錯誤

`OemSurvivalTest` 第一次跑就有一個失敗：
`Method setComponent in android.content.Intent not mocked`。

原因是我在一個宣稱「純資料、不碰 Android」的測試檔裡，寫了兩個實際建構
`Intent` 的測試。純 JVM 單元測試環境裡的 Android 類別只是**沒有實作的空殼**，
呼叫任何方法都會丟例外。

修法不是去 mock `Intent`，而是改成斷言 `components` 這份純資料本身 ——
真正會寫錯的是資料（打錯類別名、漏掉廠牌），不是那層包裝。

> **教訓：測試要對準「真正可能出錯的東西」，而不是對準最外層那個好呼叫的函式。**

**你要做的事：** 在 OPPO 上確認改完之後**沒有壞掉**。其他廠牌我們驗不了，
靠對照表 + 文字步驟兜底 —— 文字步驟是主要手段，intent 只是省下找路的力氣。

### ⬜ M5 — 封測與正式發布

⚠️ **這裡有一個會影響時程的現實限制，需要先查證最新規則：**
Google Play 對新註冊的個人開發者帳號有「先做封閉測試才能申請正式發布」的要求，
我記得的版本是**至少 12 名測試者、連續 14 天**。這條規則 Google 改過好幾次，
到了 M4 我們必須去 Play Console 看當下的實際要求，不能照我的記憶做。

如果這條仍然有效，代表你需要**找到 12 個願意裝來用兩週的人**。
這不是技術問題，是要提早準備的事——所以現在就寫在這裡。

## 明確不做的事

沿用 spec §10，並補上這個階段的新決定：

- 不做帳號、登入、雲端同步（違反零網路原則）
- 不做 iOS（要另外一套完全不同的機制，見對話紀錄的評估）
- 不加任何 analytics / crash 回報 SDK（同上，零網路）
- 不在 M3 之前碰 Mode B 的演算法調參——它需要真實使用資料，而我們還沒有使用者
